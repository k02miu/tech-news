CVECVE-2026-58053（CVSS 3.1: 9.1 AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H、CVSS 4.0 Vector: CVSS:4.0/AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:H/VA:H/SC:H/SI:H/SA:H）

影響バージョンGitea act_runner の Docker backend、<= act 0.262.0 (defaultStatus: affected)。CI/CD 自動化基盤として self-hosted Gitea を使う全環境
修正バージョン本朝刊時点でパッチ未公開（CVE Brief も "no patches were available at disclosure time" と明記）。VulnCheck アドバイザリ／PoC は公開済み

悪用状況能動的悪用の証拠なし・PoC リポジトリ公開済み
  • 概要 — OSS Git サーバ Gitea の GitHub Actions 互換ランナー act_runner は、workflow の container.options 文字列を Docker ジョブコンテナの HostConfig に流し込む。運用者が安全側に倒すため privileged: false を指定しても、その単一フラグのみを OFF にし、--pid=host／--cap-add／--security-opt などの危険な他オプションは マージされたまま 通過させる。結果としてワークフロー実行権限を持つユーザーは、ホストの namespace と広い capabilities を持つジョブコンテナを起動でき、privileged モードを無効化していてもホストの root 権限へ脱出可能
  • 被害シナリオ — Next.js／React／Hono／Node.js／Python／Java・SpringBoot 系を問わず、self-hosted Gitea 上で PR 由来のコードを act_runner でビルド・テストしている全 CI 環境が該当。前号で取り上げた pnpm ロックファイル汚染クラスターと同じPR 由来の workflow を実行するだけという低い敷居で、CI runner のシークレット・クラウドクレデンシャル・ホスト Docker daemon が掌握される。外部 PR を無審査で回している Gitea インスタンスは即危険領域
  • 修正内容 — 修正パッチは本日朝時点で未公開。VulnCheck アドバイザリ本文は container.options を HostConfig にマージする前に denylist／allowlist で危険フラグを剥がすハードニングを推奨
  • 対応 — (1) self-hosted Gitea 上で Docker backend で act_runner を運用している場合は、外部寄稿ワークフロー実行を即時停止するか、Pull Request 由来の workflow 実行を禁止 (2) runs-on／container.options の受け入れを静的バリデーションで制限し、--pid／--cap-add／--security-opt／--privileged を含む workflow を拒否 (3) runner ホストは ephemeral VM／コンテナに置き、ホストの /var/run/docker.sock をマウントしない (4) パッチ公開まで監視を継続。CVE-2026-58053 の NVD／VulnCheck を毎朝確認

🟠 Apache Kerby CVE-2026-57915 — unsupported PA-DATA type で Kerberos pre-auth bypass、認証基盤の握られ起点 HIGH

項目詳細
CVECVE-2026-57915（CVSS 7.3、CVE Brief Sunday 評価）
公表日oss-security 投稿: 2026-06-26／CVE Brief Sunday で再強調（2026-06-28）
影響バージョンApache Kerby の pre-auth check 実装全バージョン（advisory 本文待ち）
脆弱性種別CWE-287 不適切な認証／CWE-345 データ真正性検証不備
悪用状況公開PoCなし・能動的悪用の証拠なし（pre-auth bypass のため偽装成りすまし起点）
  • 概要 — Apache Directory プロジェクトの純 Java Kerberos 実装 Apache Kerby は、AS-REQ の PA-DATA にライブラリが未対応または未サポートの type を送り込まれた場合、pre-auth check を回避しリクエストを受け付けてしまう。攻撃者は認証ステップを抜けて就能erator principal として TGT を取得しうる
  • 被害シナリオ — Kerby を社内 IdP／SASL GSSAPI／Java Spring Security Kerberos 拡張で利用する環境で、pre-auth bypass は対象アカウントへの偽装成りすまし起点になる。Java/SpringBoot アプリで SPNEGO／Kerberos 認証を利用している場合は直接関連。直接インターネット露出は稀だが社内横展開で権限昇格の触媒
  • 対応 — Apache Kerby の最新安定版／スナップショットに追従（advisory 本文確認）。pre-auth strict モード／未対応 PA-DATA の拒否設定があれば有効化。Kerberos 認証経路を audit し exploited principal 痕跡を検査
